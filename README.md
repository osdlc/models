# models

This repo holds shared record types for Markdown corpora, and corpora built on them. Each package
here is published to npm and checked with the
[corpus-schema](https://github.com/osdlc/markdown/blob/main/packages/conformance/corpus-schema/SPEC.md)
validator, `@osdlc/corpus-schema`, from osdlc/markdown.

- A profile is a corpus that holds types and no records. A corpus builds on it.
- A starter corpus holds shared records that other corpora reference and cite.

## The packages

| Package                                               | Folder                  | What it is                                                              |
| ----------------------------------------------------- | ----------------------- | ----------------------------------------------------------------------- |
| [`@osdlc/corpus-profile-sdlc`](profiles/sdlc/)        | `profiles/sdlc/`        | sdlc's planning record types: principles, decisions, tasks and the rest |
| [`@osdlc/corpus-profile-claims`](profiles/claims/)    | `profiles/claims/`      | Record types for claims and the evidence behind them                    |
| [`@osdlc/corpus-sdlc-starter`](corpora/sdlc-starter/) | `corpora/sdlc-starter/` | Shared sdlc principles, typed by the sdlc profile                       |

Each package's README says what it holds and how to use it. They need `@osdlc/corpus-schema` 0.3.0
or later.

## Use them in a corpus

Install the packages in the folder that holds your corpus, or in any folder above it:

```sh
pnpm add -D @osdlc/corpus-profile-sdlc @osdlc/corpus-sdlc-starter @osdlc/corpus-schema
```

Name them in the corpus's root file. `extends` gives the corpus a profile's types, and `uses`
lets a folder at the corpus root take a type as it is, with no schema file. `references` names a
corpus whose records you cite:

```yaml
---
corpus-schema: 0
level: 2
extends:
  sdlc: "@osdlc/corpus-profile-sdlc"
references:
  osdlc: "@osdlc/corpus-sdlc-starter"
uses: [sdlc/*]
---
```

Cite a starter record by id, such as `related: ["[[P-0002]]"]`. A wikilink into a referenced
corpus needs a local copy of it, which `sync` writes to `_references/`. Commit the copy, and run
`sync` again after you update the starter:

```sh
npx @osdlc/corpus-schema sync docs/planning
npx @osdlc/corpus-schema validate --strict docs/planning
```

## Work on the packages

```sh
pnpm install
pnpm test
sh tools/tests/leak-check.sh
sh tools/leak-check.sh
```

`pnpm test` runs each package's tests. `tools/validate-strict.sh <folder>...` validates folders and
fails on a warning. `tools/leak-check.sh` fails on private data in a package folder, such as a
home path, an email address or a link into a private repo, and `tools/tests/leak-check.sh`
checks that it catches each kind. CI runs all of these on every pull
request, in `.github/workflows/validate.yml`.

## Releases

Releases use [Changesets](https://changesets.dev), as in osdlc/osdlc and osdlc/markdown.

- A change users can see adds a changeset: run `pnpm changeset` at the repository root. Start a
  breaking change's summary with `**Breaking:**`.
- On a push to main, `.github/workflows/packages-publish.yml` runs `validate.yml`, then
  osdlc/osdlc's shared `ts-packages-release.yml` with the TypeScript steps off. With changesets
  pending, that opens a Version Packages pull request as the osdlc-release GitHub App, filled by
  `pnpm run version-packages`. When that pull request merges, the push publishes the versions
  that are not on npm yet.
- npm auth is trusted publishing (OIDC) only, with provenance. Each package's trusted publisher on
  npmjs.com names repository `osdlc/models` and workflow `packages-publish.yml`, with no
  environment. Keep the workflow's file name.
- A package must be on npm before CI can publish it. The owner stages a new package once with
  `pnpm exec package-checks stage <folder>`, which publishes a placeholder and adds its trusted
  publisher.
- Each published version gets a git tag and a GitHub release named `<package>@<version>`.
